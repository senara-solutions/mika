# fix(skills/permission-policy): source-fix mika-relay TIER 1 to allow intra-platform mika ask + grooming gh issue authoring

## Overview

mika-relay's permission-policy denies `mika ask --agent mika-arch` Bash invocations during `/mika-groom-ticket` Phase 3 step 9, blocking dev-groom canaries on every grooming attempt. The denial happens because mika-relay's TIER 1 auto-approve list at `skills/bundled/permission-policy/system_prompt.md:13-20` enumerates Read/Glob/Grep, git, cargo/npm, basic shell, and `gh pr/issue view` — but does NOT include any `mika ask` invocation or `gh issue edit/comment` (which `/mika-groom-ticket` Phase 5 uses for the body amendment + closing comment).

Operator hot-fixes to the deployed `~/.mika/agents/mika-relay/skills/permission-policy/system_prompt.md` are reverted by mika-spirit's bundled-skill re-sync mechanism on every agent session start. Half-life of a hot-fix on deployed skills = one dispatch. This plan applies the same narrow allow-list expansion in the source tree (`skills/bundled/permission-policy/system_prompt.md`), which the next `make deploy` carries through `BUNDLED_SKILL_MANIFESTS` to all agents.

This is the canonical Path 2 hot-fix from the dashboard-launch plan (2026-05-02). It is intentionally narrow: enumerate the three known intra-platform peer agents and the two grooming-specific `gh issue` write verbs. Wildcard `mika ask --agent *` and `gh issue create` are explicitly out of scope (different blast radius). The durable redesign — agent registry + dispatch-classification reframe — is tracked at mika#935 (parked) and mika-platform#75 (parked).

## Problem Frame

`mika-relay`'s permission-policy receives a `[claude-pilot] ` PilotEvent for every Bash invocation in a claude-pilot session. It classifies each into TIER 1 (auto-allow), TIER 1.5 (auto-answer), TIER 2 (research-and-answer), or TIER 3 (escalate). Unrecognized commands fall through to TIER 2/3 paths that result in deny.

`/mika-groom-ticket`'s canonical pipeline issues two classes of commands that the current TIER 1 list does not enumerate:

1. **Phase 3 step 9** — sends architect briefs via `mika ask --agent mika-arch ...`. This is the load-bearing two-pass review call. Currently denied; canary v3/v4 of 2026-05-02 confirmed.
2. **Phase 5 step 19** — amends the issue body to attach `> - **Branch:**`, `> - **Plan:**`, `> - **Grooming history:**` callouts via `gh issue edit <num> --body-file <tmpfile>`. **Phase 5 step 20** — posts the closing/handoff comment via `gh issue comment <num> --body ...`. Both currently denied (the operator-bypass on mika#932 had to issue these from operator-Claude session, not from claude-pilot).

The diagnostic comment on mika#935 (https://github.com/senara-solutions/mika/issues/935#issuecomment-4363757877) identified the bundled-skill re-sync as the reason hot-fixes don't survive: `mika-spirit` writes `~/.mika/agents/<agent>/skills/<skill>/*` from `BUNDLED_SKILL_MANIFESTS` (generated by `build.rs` from `skills/bundled/`) on every agent session start. mika-relay restarts on every claude-pilot permission callback under load, so half-life is one dispatch.

This plan fixes the symptom in source so the next deploy carries the change durably. The structural fix (agent registry replacing literal-string TIER 1 enumeration) is parked.

## Requirements Trace

- **R1** — `claude-pilot` session calling Bash `mika ask --agent mika-arch ...` from inside `/mika-groom-ticket` Phase 3 step 9 receives `{"action": "allow"}` from mika-relay's permission-policy. (Acceptance criterion 1.)
- **R2** — Sibling intra-platform calls `mika ask --agent mika-dev ...` and `mika ask --agent mika-qa ...` are also allowed. They share the same denial pattern; enumerating only `mika-arch` would leave foreseeable future grooming/qa pipelines blocked.
- **R3** — `gh issue edit <num> ...` and `gh issue comment <num> ...` invocations from inside grooming Phase 5 (step 19/20) are allowed. Without these, claude-pilot cannot complete grooming end-to-end.
- **R4** — `mika ask --agent *` (wildcard) and `gh issue create` are NOT auto-allowed. These have different blast radii (unknown peers / new GitHub state) and remain in TIER 2/3 paths.
- **R5** — Documentation reflects the bundled-skill re-sync mechanism so future operators understand why hot-edits on `~/.mika/agents/.../skills/*` files do not survive.
- **R6** — All three verification commands pass: `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --all`, `mika skills validate`.

## Key Technical Decisions

- **Source-tree edit, not deployed hot-fix.** Hot-fixes on `~/.mika/agents/mika-relay/skills/...` are reverted by bundled-skill re-sync within one agent restart (mika-relay restarts ~100x per day under load). Source-tree edit propagates through `BUNDLED_SKILL_MANIFESTS` on next deploy and is durable.
- **Narrow allow-list, not wildcard.** Three named intra-platform peers (`mika-arch`, `mika-dev`, `mika-qa`) instead of `mika ask --agent *`. Rationale: limits blast radius to the platform's well-known dispatch trinity; future custom agents fall through to TIER 2/3 by default. The durable agent-registry design (mika#935) replaces this enumeration when it ships.
- **`gh issue edit` and `gh issue comment` IN scope; `gh issue create` OUT.** edit/comment are platform-prescribed writes (canonical `/mika-groom-ticket` Phase 5 steps); create is freelance shell with broader implications. Asymmetry is deliberate.
- **Inline HTML comment with cross-reference to mika#935.** Marks the edit as a hot-fix anchored to a tracked durable-fix ticket. Reviewers reading the prompt see the rationale immediately and can grep for `HOT-FIX 2026-05-02`.
- **Doc paragraph in `docs/runtime-structure.md`.** Existing canonical reference for `~/.mika/` layout. New paragraph belongs under "Directory Layout" because it describes the mechanism that populates the skills directory. No new file needed.
- **No code changes.** Permission-policy is prompt-only (no `tools.json`, no `handlers/`). The runtime classifier is the LLM evaluating the prompt against incoming PilotEvents. Source-tree change to the prompt file is the entire delivery surface.

## System-Wide Impact

- **Interaction graph:** mika-relay's permission-policy is the gate for every claude-pilot Bash/Edit/Skill call. The change adds two new positive matches in TIER 1; everything else continues to flow through the existing classifier. No new tool surfaces, no new event types.
- **Error propagation:** Unchanged. Unknown commands still fall through to TIER 2 (research-and-answer) or TIER 3 (escalate to Vincent + deny). The two new TIER 1 entries shorten the path for a narrow set of commands; they do not create new failure modes.
- **State lifecycle risks:** None. Prompt-only change. No DB schema, no migration, no on-disk state change beyond the file itself. `gh issue edit` and `gh issue comment` produce side effects on GitHub, but those side effects are exactly what `/mika-groom-ticket` Phase 5 already prescribes — the change just lets claude-pilot do them instead of forcing operator-Claude.
- **API surface parity:** mika-relay is the only agent with `permission-policy` enabled (other agents have it disabled via DB override). The source change propagates to all agents on `make deploy`, but only mika-relay actually evaluates the prompt during PilotEvents. No other agent's behavior changes.
- **Integration coverage:** Live canary on mika#931 is the only test that proves the full path (PilotEvent → TIER 1 classification → allow → claude-pilot continues). Schema-level review can confirm the bullets are well-formed; only live invocation proves the LLM classifier honors them.
- **Unchanged invariants:**
  - The `[claude-pilot] ` activation gate at the top of the prompt is unchanged. New TIER 1 entries inherit it; they do not apply to operator-shell or webhook contexts.
  - TIER 3 deny-list (`rm -rf`, `git push --force`, `gh label delete`, etc.) is unchanged. Destructive operations remain escalation-required regardless of the new TIER 1 entries.
  - `mika ask --agent *` wildcard, `gh issue create`, and other broader patterns remain in TIER 2/3 paths.
