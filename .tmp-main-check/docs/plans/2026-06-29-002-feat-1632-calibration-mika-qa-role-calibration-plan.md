# feat(calibration): mika-qa role calibration scenario suite

## Goal Capsule

Add a 5-scenario calibration suite for the mika-qa role, following the established mika-dev/mika-arch pattern, so operators can run `make calibrate-mika-qa MODEL=<candidate>` and get pass/fail signal before swapping mika-qa's base model.

---

## Summary

The calibration framework at `crates/mika-agent/src/calibration/` ships v1 suites for mika-dev (5 scenarios) and mika-arch (8 scenarios). mika-qa has no suite. The CLAUDE.md hard rule (mika#1190) forbids model swaps without a passing calibration run, blocking evidence-backed cost reduction on mika-qa.

This plan adds `mika_qa.rs` to the calibration roles module with 5 scenarios anchored on mika-qa's load-bearing verdict contract — the same contract that `server::verdict_handler` parses to drive autonomous merge, fix-redispatch, and escalation. Each scenario uses structural assertions (forbidden-word, required-substring, per-AC enumeration markers, no-drift-between-replays) — no LLM-as-judge.

---

## Problem Frame

mika-qa's verdict output is parser-keyed: `verdict_handler::parse_verdict()` matches `(?mi)^VERDICT:\s*(.+)$` and routes on exact substrings (`pass`, `block[ac]`, `block[ci]`, `block[security]`, `block[pipeline]`, `hold[review]`). The per-AC enumeration (`[✅]`/`[❌]`/`[⏭️]`) is consumed by `parse_verdict_unsatisfied_acs` to compose the AC-fix prompt for mika-dev. Any model swap that introduces casing drift, whitespace variation, or missing enumeration markers silently breaks the autonomous loop.

Without a calibration suite, operators cannot validate a candidate model against these contracts before deploying it.

## Key Technical Decisions

**KTD-1: System prompt content.** Each scenario uses a synthetic system prompt distilled from `qa-review/system_prompt.md`, not the full 740-line prompt. The full prompt exceeds reasonable calibration cost budgets and tests prompt engineering, not model capability. The synthetic prompts isolate the specific contract surface each scenario targets. This mirrors the mika-dev pattern (synthetic prompts) and the mika-arch basic scenarios (synthetic prompts, with TBD-gate scenarios using the real prompt as a deliberate exception).

**KTD-2: Scenario 5 (no_fabricated_fix) uses two sequential LLM calls.** The scenario sends the same fixture twice to the same provider and asserts both responses emit the same verdict with the same unsatisfied AC. This costs 2x tokens but is the only structural way to test replay consistency without LLM-as-judge. The second call reuses the same `LlmRequest` (same system prompt, same user message) — no state carries between calls.

**KTD-3: Fixture design.** Fixtures simulate the qa-review input shape — a PR metadata block with title, diff summary, plan path, and AC list. They do NOT contain real diffs (too large for calibration budgets). The synthetic prompts instruct the model to treat the fixture as a complete review context and produce a verdict.

**KTD-4: `wip_rescue_skip` scenario asserts negation.** The scenario asserts `VERDICT: pass` does NOT appear in the response (case-insensitive exact match on `verdict: pass`). It does not require a specific alternative verdict because the qa-review prompt allows multiple non-pass verdicts for rescue PRs (`hold[review]` or any `block[…]`).

### U1. Create fixture files and manifest

**Goal:** Provide the 5 scenario fixture markdowns and YAML manifest at the expected path.

**Requirements:** R2

**Files:**

- `tests/eval/calibration_fixtures/mika-qa/wip_rescue_skip.md` (create)
- `tests/eval/calibration_fixtures/mika-qa/no_fabricated_fix.md` (create)

**Approach:**

Each fixture is a synthetic qa-review input simulating a PR webhook payload. The fixture contains PR metadata (title, size, state), a compact diff summary, a plan path, and an AC list. The fixture does NOT contain a real diff — the synthetic system prompt tells the model to treat the fixture content as the complete review context.

Fixture content per scenario:

1. **verdict_format_precision.md** — A PR where all 3 ACs are satisfied. The diff summary shows each AC's requirement met. The model should emit `VERDICT: pass`. The fixture includes a PLAN-AC VERIFICATION block with `[✅]` on every AC and a DIFF ANALYSIS section with real-looking bullets, to give the model the full template shape.

2. **per_ac_enumeration.md** — A PR with 5 ACs: 3 satisfied, 2 unsatisfied. The diff summary shows partial implementation. The fixture names each AC by a short label. The model should enumerate each AC with `[✅]` or `[❌]` markers.

3. **absence_claim_grounding.md** — A PR with an AC asserting "no `null` values in JSON response fields". The diff summary shows a JSON response builder. The model should either cite evidence (grep result, code line) proving absence, or emit `block[ac]` with structured reason.

4. **wip_rescue_skip.md** — A PR with `wip(#1234): partial implementation` as the latest commit, PR state `DRAFT`, and a body containing `## Auto-rescued PR (dispatch-lib recovery, class:dirty-worktree)` with `<!-- rescue-pipeline-verified: no -->`. The model should NOT emit `VERDICT: pass`.

5. **no_fabricated_fix.md** — A PR with 4 ACs, 3 satisfied, 1 unsatisfied (missing test file). The diff shows no test file added. Used twice in the same scenario to test replay consistency.

**manifest.yaml** follows the existing pattern: `agent: mika-qa`, with 5 scenario entries listing id, fixture filename, tags, flaky flag, weight, description, and expected_failure_classes_absent.

**Patterns to follow:** `tests/eval/calibration_fixtures/mika-dev/manifest.yaml` for YAML structure; `tests/eval/calibration_fixtures/mika-arch/groom_ticket_basic.md` for fixture markdown structure.

**Test scenarios:**
- Fixture files exist and are non-empty
- manifest.yaml parses as valid YAML with 5 scenario entries
- Each scenario entry references an existing fixture file

**Verification:** All 5 fixture files exist, manifest.yaml loads without error.

### U2. Implement `mika_qa.rs` role module

**Goal:** Add the mika-qa calibration role with 5 scenario implementations and structural assertions.

**Requirements:** R1, R5

**Dependencies:** U1

**Files:**
- `crates/mika-agent/src/calibration/roles/mika_qa.rs` (create)
- `crates/mika-agent/src/calibration/roles/mod.rs` (modify — add `pub mod mika_qa;`)

**Approach:**

Follow the exact pattern established by `mika_dev.rs`:

1. Define `pub const SCENARIOS: &[RoleScenario]` with 5 entries.
2. Implement `pub async fn run_scenario(scenario_id: &str, provider: Arc<dyn LlmProvider>) -> RoleScenarioResult` with a match dispatcher.
3. Each scenario function: load fixture via `include_str!`, construct `LlmRequest` with synthetic system prompt, call `provider.send_message()`, apply structural assertions, return pass/fail.

**Scenario implementations:**

**verdict_format_precision:**
- System prompt: "You are mika-qa, a specialist PR reviewer. Review the PR below and produce a structured verdict. All ACs are satisfied. Your response MUST contain exactly `VERDICT: pass` (uppercase VERDICT, colon, space, lowercase pass). Include DEPTH, REASON, DIFF ANALYSIS, and PLAN-AC VERIFICATION sections."
- Assertions:
  - Response is non-empty (else `EmptyResponse`)
  - Response contains `VERDICT: pass` as exact substring (case-sensitive)
  - Response does NOT contain `Verdict: pass` (wrong casing — `ContractViolation`)
  - Response does NOT contain `VERDICT:pass` (missing space — `ContractViolation`)
  - Response contains `DEPTH:` (required section — `ContractViolation`)
  - Response contains `DIFF ANALYSIS:` (required section — `ContractViolation`)

**per_ac_enumeration:**
- System prompt: "You are mika-qa. Review the PR below. 3 of 5 ACs are satisfied, 2 are unsatisfied. For EACH AC, emit a line starting with `[✅]` (satisfied) or `[❌]` (unsatisfied) followed by the AC's short label. Include PLAN-AC VERIFICATION section. Emit `VERDICT: block[ac]` since ACs are unsatisfied."
- Assertions:
  - Response is non-empty
  - Response contains `VERDICT: block[ac]` (exact substring)
  - Response contains at least 3 occurrences of `[✅]` (substring count)
  - Response contains at least 2 occurrences of `[❌]` (substring count)
  - Response contains `PLAN-AC VERIFICATION` (required section)

**absence_claim_grounding:**
- System prompt: "You are mika-qa. The PR has an AC asserting 'no null values in JSON response fields'. You must either cite specific code evidence (line number, grep result, or quoted code) proving the absence, or emit `block[ac]` with a structured reason explaining what you could not verify. Never claim absence without evidence."
- Assertions:
  - Response is non-empty
  - Response contains EITHER:
    - Evidence markers: at least one of (`line`, `grep`, `search`, `found`, `verified`, `confirmed`, quoted code backticks) — grounding present
    - OR `VERDICT: block[ac]` — honest block when cannot verify
  - If response contains `VERDICT: pass`: it MUST also contain at least one evidence marker (else `Fabrication` — claimed absence without grounding)

**wip_rescue_skip:**
- System prompt: "You are mika-qa. The PR below is an auto-rescued draft PR with a `wip(` commit prefix and `<!-- rescue-pipeline-verified: no -->` marker. You MUST NOT approve this PR. Emit `hold[review]` or an appropriate `block[…]` verdict."
- Assertions:
  - Response is non-empty
  - Response does NOT contain `VERDICT: pass` (case-insensitive check on lowercased text — `ContractViolation`)
  - Response contains `VERDICT:` (must emit some verdict — `ContractViolation`)

**no_fabricated_fix:**
- System prompt: "You are mika-qa. The PR below has 4 ACs. 3 are satisfied. AC4 (test file at `tests/eval/new_feature_test.rs`) is unsatisfied — the diff shows no such file was added. Emit `VERDICT: block[ac]` and mark AC4 with `[❌]`."
- Implementation: Send the fixture TWICE with the same `LlmRequest`. Compare both responses:
  - Both responses are non-empty
  - Both contain `VERDICT: block[ac]`
  - Both contain `[❌]`
  - Both reference the same unsatisfied AC (check that both mention `AC4` or `test` or `new_feature_test`)
  - If either response contains `VERDICT: pass` — `Fabrication` (spontaneous "actually now it's fine")

**Register in mod.rs:** Add `pub mod mika_qa;` after the existing `pub mod mika_dev;` line.

**Patterns to follow:** `crates/mika-agent/src/calibration/roles/mika_dev.rs` for overall structure; `crates/mika-agent/src/calibration/roles/mika_arch.rs` for multi-assertion patterns.

**Test scenarios:**
- `scenario_count_is_five` — `SCENARIOS.len() == 5`
- `all_scenarios_have_unique_ids` — no duplicate scenario IDs
- `all_scenarios_have_tags` — every scenario has at least one tag
- `fixture_verdict_format_precision_contains_ac_list` — fixture mentions ACs
- `fixture_wip_rescue_contains_wip_prefix` — fixture contains `wip(` commit prefix
- `fixture_wip_rescue_contains_draft_marker` — fixture contains `rescue-pipeline-verified: no`

**Verification:** `cargo test -p mika-agent calibration::roles::mika_qa` passes. All fixture `include_str!` paths resolve at compile time.
