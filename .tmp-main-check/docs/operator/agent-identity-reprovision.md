# Re-provisioning an agent's `identity.toml`

An agent whose `identity.toml` is missing or unreadable starts **fail-closed**:
zero skills, every mutational built-in tool denied. It answers, but it can do
nothing. This page is how you get it back. (A *malformed* file fails closed too
for a well-known agent — but not for a user-defined one, which is the one case
that fails the other way; see § 5.)

It is also the page that says the thing you most need to know before you delete
anything: **a deleted `identity.toml` is never regenerated by restarting.**

Since mika#2230 there is a verb for the repair — `mika agents reprovision` (§ 7).
Read § 1 first anyway: three faults arrive here and only one of them is the verb's
business.

---

## 1. Diagnose — three causes, three remediations

The three faults are logged under distinct event names precisely because they
need different gestures. Read the log before acting:

```sh
grep -E 'identity_toml_(absent|unreadable|malformed)' "$MIKA_SPIRIT_LOG_FILE"
```

| Event | Meaning | Go to |
|---|---|---|
| `identity_toml_absent` | The file does not exist. | § 3 |
| `identity_toml_unreadable` | The file exists but the process cannot read it (permissions, I/O). | § 4 |
| `identity_toml_malformed` | The file exists and is readable, but is not valid TOML — or fails `[skills]` validation. | § 5 |

Each line carries `agent` and `path`, so the offending agent and file are named.

> Steady state is **zero lines**. Any hit is an agent whose skill boundary is
> not the one its identity file was meant to define — normally no skills at all,
> and in the single case described in § 5, all of them.

For a well-known agent (`mika-dev`, `mika-qa`, `mika-arch`, `mika-test`) also
check for the neighbouring reconciliation signal, which fires from the same
cause and is easy to mistake for an unrelated warning:
`grep identity_reconcile.skipped "$MIKA_SPIRIT_LOG_FILE"`.

> **One case on this page is already served by a restart, and it is worth not
> confusing with the others.** For a **well-known** agent whose `identity.toml`
> is *present but drifted* — a code-owned section edited by hand, a static-spec
> change that never landed — `reconcile_well_known_identity` re-applies
> `CODE_OWNED_IDENTITY_SECTIONS` at every startup, `MIKA_DISABLE_AGENT_PROVISIONING`
> included (mika#2330). Restarting is the whole remedy there. What has no
> startup path, and is what § 7's verb exists for, is **absence** (the
> reconciler reads the file first and returns early when the read fails — it
> needs a file to reconcile, it does not create one), the same absence on a
> customer agent with no spec to reconcile against, and `soul.md`, which the
> reconciler never touches at all.

---

## 2. Why restarting does not fix it

This is the part that costs people an outage, so it is stated plainly.

The classic tier remediation — *set `MIKA_AGENT_TIER`, delete `identity.toml`
and `soul.md`, restart, let bootstrap rewrite them* — **does not work.** The
files are not rewritten. Deleting them deletes them, permanently.

Three independent gates each decline to rewrite the file:

- `bootstrap_fresh_install` runs only when `home::is_initialized()` is false,
  and that returns true as soon as `{MIKA_HOME}/data/mika.db` exists. Any tenant
  that has ever run is initialized for ever.
- `home::bootstrap` writes through `write_default_if_missing`, so it would
  restore the file — but nothing calls it for an already-provisioned agent. The
  CLI's own guard (`ensure_initialized_for_agent`) tests for `config.toml`, not
  `identity.toml`, so an agent missing only its identity looks fully provisioned.
- For a **well-known** agent, startup provisioning takes the *existing-agent*
  branch and calls `reconcile_well_known_identity`, which reads the on-disk file
  first and returns early when the read fails. Reconciliation needs a file to
  reconcile; it does not create one.

Before mika#2027 the consequence was worse than an agent with no identity: a
missing file yielded `Identity::default()`, whose `skills.allowlist` is `None`,
which the allowlist filter treats as *no filter at all* — every bundled skill
active, `shell-exec` / `git-ops` / `github` / `tmux` included. **Deleting an
agent's identity file widened it.** That is now closed: absence fails closed.
The remediation below is what replaces the delete-and-restart reflex.

---

## 3. Remediation — the file is absent

**The supported gesture is § 7's verb.** This section is the fallback for when
the `mika` binary is not available on the host, and the reference for what the
verb writes — read it if you are hand-writing the file, skip to § 7 otherwise.

### 3a. Pick the right template

| Agent | Template (source of truth) |
|---|---|
| Personal / customer agent, operator tier | `DEFAULT_IDENTITY` in `crates/mika-common/src/home.rs` |
| Personal / customer agent, family tier | `FAMILY_IDENTITY` in `crates/mika-common/src/home.rs` |
| `mika-dev` | `MIKA_DEV_IDENTITY` in `crates/mika-agent/src/well_known_agents.rs` |
| `mika-qa` | `MIKA_QA_IDENTITY` in `crates/mika-agent/src/well_known_agents.rs` |
| `mika-test` | `MIKA_TEST_IDENTITY` in `crates/mika-agent/src/well_known_agents.rs` |
| `mika-arch` | computed by `build_mika_arch_identity()` — see § 3d |

The well-known set is `WELL_KNOWN_AGENTS` in that same file; read it there rather
than from memory. (`mika-relay` was retired in mika#1193 and is not in it, though
some prose still names it.)

The tier of a customer agent is whatever `MIKA_AGENT_TIER` was set to when it
was first bootstrapped, **not** what the environment says today. If you are
unsure which one it is, `soul.md` answers it: a family-tier soul carries the
`FAMILY_SOUL_MARKER` sentinel.

### 3b. Write it

```sh
# On the container/host, as the user the agent runs as:
$EDITOR ~/.mika/agents/<agent>/identity.toml   # paste the template's content
chmod 600 ~/.mika/agents/<agent>/identity.toml
```

**Copy the tier template. Do not improvise the file** — the `[skills].allowlist`
it carries *is* the agent's boundary, and a hand-written one grants whatever you
happened to remember.

Two traps in this file, both of which read as harmless:

> **An empty or absent `[skills].allowlist` inside a *present* file is
> permissive, not restrictive.** `apply_identity_allowlist` returns early on an
> empty list, so `allowlist = []` means "no filter" — every bundled skill active.
> Only a missing *file* is fail-closed. Restricting an agent means listing the
> skills it may use, explicitly.

> **A minimal `name`/`emoji`-only file is therefore the widest one you can
> write.** It is a legitimate emergency stopgap to get a stuck agent answering,
> but it is not a repair: it restores exactly the permissive state mika#2027
> closed. Follow it with the real template in the same maintenance window.

### 3c. Restart and verify

```sh
# restart mika-spirit (rc-service / systemctl / kubectl rollout restart — per host)
grep -E 'identity_toml_(absent|unreadable|malformed)' "$MIKA_SPIRIT_LOG_FILE" | tail
mika skills list --agent <agent>
```

The grep must return nothing new after the restart, and `skills list` must show
the skills the tier grants. An empty skill list means the file is still not being
read — re-read § 1 rather than restarting again.

> **`~/.mika/agents/<agent>/skills/` will look emptied, and that is expected.**
> Startup materializes one symlink per allowed bundled skill and removes the
> symlinks for the rest, so a fail-closed start strips them all. Only symlinks
> into the shared library are removed — marketplace and `--copy-managed` skill
> directories are left alone — and the symlinks come back on the first restart
> after the identity is valid. Do not reinstall skills to "repair" this.

### 3d. `mika-arch` only

mika-arch's identity is *computed*, not a static constant: its `[kg].docs_roots`
must contain absolute paths, derived at provision time from `MIKA_KG_DOCS_ROOTS`.
Hand-writing it means hand-writing those absolute paths. Make sure
`MIKA_KG_DOCS_ROOTS` is set in the service environment, and see
`crates/mika-agent/CLAUDE.md` § Multi-Corpus Support for the expected shape.

## 4. Remediation — the file is unreadable

`identity_toml_unreadable` is a permissions or I/O fault, not a missing file.
**Do not re-provision it** — you would overwrite content that is still there.

```sh
ls -l ~/.mika/agents/<agent>/identity.toml
# expected: -rw------- (0600), owned by the user mika-spirit runs as
chown <mika-user> ~/.mika/agents/<agent>/identity.toml
chmod 600 ~/.mika/agents/<agent>/identity.toml
```

Then restart and verify as in § 3c.

---

## 5. Remediation — the file is malformed

The log line carries the parse error. Fix the TOML in place:

```sh
$EDITOR ~/.mika/agents/<agent>/identity.toml
```

Note the residual asymmetry, so a green start does not mislead you: a **user-defined**
agent with a *malformed* file falls back to the permissive default identity
(mika#811 behaviour, unchanged), while a **well-known** agent fails closed. An
absent file fails closed for both. So a user-defined agent with a broken
`identity.toml` may look like it is working while running with every bundled
skill active — the `identity_toml_malformed` line is the only signal, which is
why § 1 greps for all three names rather than just the two that neuter the agent.

## 6. Changing an agent's tier

The founding incident of mika#2027 was a tier change, so: the delete-and-restart
route does not exist (§ 2).

```sh
# 1. put the tier in the SERVICE environment — not in this shell
$EDITOR /etc/conf.d/mika-spirit     # or the systemd drop-in / K8s ConfigMap
#    MIKA_AGENT_TIER=family

# 2. write BOTH templates to disk
mika agents reprovision <agent> --tier family

# 3. restart mika-spirit
```

**Both files, always.** A tier has two axes since mika#2023 — `identity.toml`
carries the tools, `soul.md` carries the persona — and the mika#1962 boot guard
detects family provisioning on **either** of them. Writing one alone fabricates
the exact drift that guard exists to report; the verb writes both by default, and
`--identity-only` prints a warning saying so.

**Step 1 is not optional and its failure is process-wide.** The tier is read once
per process and cached (mika#1962), so:

- Setting or unsetting the variable on a running process does nothing.
- If the agent is family-provisioned on disk while the process tier is not
  family, mika-spirit **refuses to start** and names the offending agent — and
  that refusal `bail!`s out of `run_server`, so *every other agent goes down with
  it*. The verb prints this warning before asking for confirmation. It is the
  guard doing its job: a hard stop beats an agent silently served under the wrong
  policy.
- **The reverse direction is not guarded.** Moving an agent from family back to
  operator removes the markers, and nothing detects the mirror-image drift — the
  guard only looks for *family* provisioning. The verb says so; no line of code
  can prevent it without inventing an operator-side sentinel, which is a separate
  change.

## 7. Tooled path — `mika agents reprovision`

```sh
mika agents reprovision <agent> [--tier default|family|champion]
                                [--identity-only] [--dry-run] [--yes]
```

Re-applies the **authoritative** `identity.toml` and `soul.md` for an agent that
already exists. One command, two populations, dispatched on the agent's name:

| Agent | Source of truth | `--tier` |
|---|---|---|
| Well-known (`mika-dev`, `mika-qa`, `mika-arch`, `mika-test`) | its code spec, mika-arch's computed `[kg].docs_roots` included | **refused** — its identity derives from no tier |
| Personal / customer agent | the tier's `identity.toml` + `soul.md` templates | `--tier`, else `MIKA_AGENT_TIER`, else operator |

Start with `--dry-run`: it prints the tier it resolved **and where that tier came
from**, the per-file verdict (absent / identical / differs), the backup paths, and
the tier warnings of § 6 — then writes nothing.

**What it guarantees.**

- *Differential.* A file already identical to the template is neither rewritten
  nor backed up, so re-running is a no-op and the mika#2027 case — identity gone,
  persona intact — touches exactly one file.
- *Reversible.* Anything overwritten is copied to
  `<file>.bak.<YYYYMMDDTHHMMSSZ>` beside it, `0600`, byte for byte. Writes are
  `.tmp` + `rename`, so a crash never leaves a partial identity.
- *Fail-closed.* It refuses to write a template that is not valid TOML, or whose
  `[skills].allowlist` is absent or empty — an empty allowlist is **not** a
  restriction (§ 3b), and a repair tool able to write the widest configuration in
  the system without saying so would be worse than the hand gesture it replaces.
  A well-known agent whose identity cannot be rendered (mika-arch without
  `MIKA_KG_DOCS_ROOTS`) is refused rather than written half-way.
- *Bounded.* It never touches `config.toml` (that is where an operator's
  `llm_provider` lives — mika#2330), never touches the database, and
  re-materializes no skill symlink.
- *Self-checking.* After writing it runs the per-agent tier guard against the
  tier **this process** resolves and prints the verdict. A failure is not rolled
  back: the disk is now coherent with the tier you asked for; it is the service
  environment that is not (§ 6, step 1).

**Two things it deliberately does not do.**

- It does not read the *service's* environment — a CLI structurally cannot. That
  half is § 6 step 1, and the verb prints the reminder rather than pretending to
  check it.
- It does not hot-reload. The tier and the skill registry are cached per process
  (mika#1962); the restart is the contract, and the command's closing lines say so
  instead of leaving it to be assumed.

**After it runs**, in this order:

```sh
mika skills list --agent <agent>        # reads identity.toml live — works BEFORE the restart
# restart mika-spirit
grep -E 'identity_toml_(absent|unreadable|malformed)' "$MIKA_SPIRIT_LOG_FILE" | tail
```

`~/.mika/agents/<agent>/skills/` may look empty until that restart. That is
expected (§ 3c) — `skills list` is what answers the question meanwhile, and
reinstalling skills to "repair" it only hides the real state.

**Where it does not apply.** An *unreadable* file (§ 4) is refused by name: its
content is still there, and overwriting it would destroy what a `chmod` recovers.
A *malformed* file (§ 5) is fixed in place — the verb would happily replace it,
but that discards whatever the operator had written in it.
