# Mika - AI Executive Assistant

## Project Overview

Mika is a conversation-first AI executive assistant with per-customer container isolation. Each customer gets their own agent container with SQLite storage. A shared gateway (`mika-gateway`) routes Telegram messages to the correct container.

**Current phase:** Phase 4 — Deployment infrastructure (Dockerfiles done, CI/CD done).

## Stack

- **Language:** Rust (edition 2024)
- **Agent engine:** Explicit Rust loop (no framework) — retrieve context → build prompt → LLM API → match stop_reason → execute tools or respond
- **LLM:** Multi-provider via `LlmProvider` trait — 11 supported providers, each with its own `model`, `api_key`, and `base_url` fields in config. Active provider selected by `llm_provider` config key. Providers: Anthropic (default, Claude Sonnet 4.6), OpenAI, OpenRouter, Groq, Ollama, Mistral, Google (Gemini), DeepSeek, MiniMax, Kimi, Qwen. All non-Anthropic providers use the `OpenAiCompatibleProvider` adapter. TUI `/provider` command for interactive switching.
- **Database:** SQLite via rusqlite (single DB per container at `~/.mika/data/mika.db`)
- **HTTP server:** Axum 0.8 (mika-server binary) with tower-http middleware
- **HTTP client:** reqwest 0.12 with rustls-tls (Claude API client with typed errors, retry, and prompt caching)
- **Async runtime:** tokio
- **MCP client:** rmcp 0.17 (official Rust MCP SDK) — stdio and Streamable HTTP transports
- **Config:** config-rs with `MIKA_` env prefix + dotenvy for `~/.mika/.env` secrets
- **Logging:** tracing + tracing-subscriber (JSON for prod, pretty for dev) + optional OpenTelemetry export via `telemetry` feature flag
- **Telemetry:** opentelemetry 0.31 + tracing-opentelemetry 0.32, feature-gated OTLP HTTP export (Langfuse-compatible)
- **Dashboard:** React 19 + TypeScript + Vite + Tailwind CSS v4 + TanStack React Query — observability dashboard SPA. In production, embedded into the mika-server binary via `rust-embed` and served at `/dashboard/*` (controlled by `MIKA_DASHBOARD_ENABLED`, default `false`). In development, runs as standalone Vite dev server on `:5173` proxied to mika-server API. Token injection via `window.__MIKA_CONFIG__` in embedded mode; `VITE_MIKA_DASHBOARD_TOKEN` env var in dev mode. Shared UI components (`@senara-solutions/ui`) extracted into `packages/ui/` (npm workspace).

Open TUI or start server to receive results.`); `--task-id <uuid>` marks callback task complete and exits; `--session-id <id>` reuses an existing session; `--parent-task-id <id>` sets `is_task_context: true` for work item guard; `--model <model>` overrides the LLM model for this invocation only (not persisted). 100KB result limit. Scoped flags: `--agent <name>` (override active agent, most subcommands), `--team <name>` (team mode, chat and ask, mutually exclusive with `--agent` and `--model`). `mika ask --team <name> "goal"` runs the full team cycle non-interactively (progress to stderr, deliverable to stdout); `--format json` extends the schema with `team_run` metadata. `--run-id <uuid>` (requires `--team`) references a previous run's workspace as read-only context; `--last-run` (requires `--team`, conflicts with `--run-id`) resolves to the most recent finished team run automatically. Warnings are shown for non-existent run IDs or team name mismatches. `mika teams log <name>` shows full run UUIDs (copyable for `--run-id`), supports `--format text|json` and `-n/--limit` (default 10). Team mode streams `TeamEvent` callbacks, split-pane dashboard, `/verbose` toggles agent responses; team runs persisted to shared DB. Run-scoped workspace directories: each run creates `workspace/{run-uuid}/` with `.meta/` subdirectory for engine metadata (goal.md, assignments.md, critic_feedback.md, deliverable.md). TUI slash commands: `/think`, `/model`, `/agent`, `/undo`, `/rewind`. Footer shows dashboard status indicator with clickable `[start]`/`[stop]` and `[open]` buttons that control the embedded dashboard on mika-server via API. Shell-like Tab completion with context-aware argument completers. Multi-line input via Alt+Enter (primary) or Shift+Enter. Image paste (Ctrl+V), persistent per-agent input history, mouse scroll, click-drag text selection with clipboard copy, bracketed paste (100KB limit).

## Conventions

- **Error handling:** `anyhow::Result` for application code, `thiserror` for library errors (e.g., `ClaudeApiError`)
- **Naming:** snake_case for functions/variables, PascalCase for types, SCREAMING_SNAKE for constants
- **Edition 2024:** `unsafe` blocks required for `std::env::set_var` etc.
- **Testing:** `#[cfg(test)] mod tests` inline in each module, `cargo test` to run
- **No framework:** The agent loop is a plain Rust async function, not a framework
- **Doc sync:** `docs/` is the single source of truth. `crates/mika-agent/build.rs` copies docs into `OUT_DIR` at build time via `include_str!(concat!(env!("OUT_DIR"), ...))`. Crate-local copies in `crates/mika-agent/docs/` are fallbacks for crates.io; sync them with `scripts/sync-agent-docs.sh` before publishing.
- **Proactive state checking:** The system prompt instructs the agent to check existing state (via `list_reminders`, `search_memory`) before any write operation (reminders, facts, people, events). This prevents duplicates after conversation compaction. New write tools should have a corresponding query tool. The system prompt also instructs the agent to check its own files (`list_agent_files`, `read_agent_file`) and documentation (`get_documentation`) before answering questions about its own configuration or internals — reinforced by the `self-knowledge` skill's always-on prompt.
- **Grounding rule:** The system prompt prohibits the agent from claiming the state of downstream or adjacent systems (PR status, CI pipeline, deploy, merge readiness) unless a tool result explicitly confirms that state. Includes BAD/GOOD examples. Reinforced in `format_callback_framing` (covers both CLI and silent callback paths) and the `SilentTrigger::Callback` trigger context.
- **Confirmation before action:** The system prompt includes a guardrail instructing the agent to answer informational questions directly without starting multi-step workflows. If follow-up action may be useful, the agent suggests it and waits for confirmation.
- **Context priority:** The system prompt establishes a conflict-resolution ordering for information sources: current user message > core memory > active skill context > conversation summary > conversation history > search results. This reduces hallucination when multiple sources disagree. See `docs/memory-classification.md` for the full deterministic vs. agent-triggered memory operation classification.
- **Database:** Case-insensitive COLLATE NOCASE on unique text columns.
- **Secrets:** `Settings` has manual `Debug` impl that redacts API key and OTLP auth header. API key errors are opaque. Exec handler executor scrubs all MIKA_* env vars from child processes (defense-in-depth). Shell-exec and github handlers additionally `unset` specific vars in their scripts. MCP child processes use `env_clear()` + allowlist. Git subprocesses scrub MIKA_* vars and set `GIT_TERMINAL_PROMPT=0`.
- **A2A Protocol (Agent-to-Agent):** `crates/mika-a2a/` implements A2A protocol v0.3. `mika-server` exposes `/a2a/{agent_name}` (JSON-RPC POST, 2MB limit) and `/a2a/{agent_name}/agent.json` (Agent Card GET), both internal-token auth. Gateway proxies at `/a2a/{customer_id}/{agent_name}` with API key auth (SHA-256 hashed keys in Postgres `a2a_api_keys` table, migration 003). A2A tasks use `trigger_type='a2a'` in the `tasks` table with orthogonal persistence: `a2a_task_map` maps A2A task IDs to internal task/session IDs; `a2a_artifacts` and `a2a_push_notification_configs` store A2A-specific data. State machine validates transitions (submitted → working → completed/failed/canceled). SSE streaming for `message/send`. `a2a_call` builtin tool (120s timeout) sends messages to remote A2A agents.
- **Tools:** Each tool validates inputs (empty check + 10,000 char max). `ToolContext` contains `{ db, session_id, trace_id, home_dir, global_home_dir, core_memory_edit_count, is_onboarding, message_sender, embedding_client, brave_api_key, github_token, skills_dirty, is_reflection, is_task_context, is_callback_turn }`. `global_home_dir: Option<&Path>` is `Some` for conversation mode (from `AgentParams.global_home_dir`), `None` for silent/team/delegate modes (blocks cross-agent file access). Tool trait uses `#[async_trait]` (Send futures, required for `tokio::spawn` in server handlers). Per-tool timeout override via `timeout_secs()` default method (returns `None` → uses 30s default). Shared `validate_and_resolve_path(path, base_dir, create_parents: bool)` helper in `tools/mod.rs` for path security (tilde expansion to base_dir, `~username` rejection, empty check, length limit, absolute rejection, traversal inspection, symlink check, canonicalize containment) — `create_parents: true` for write tools (creates dirs), `false` for read-only tools — used by `write_agent_file`, `write_workspace`, `read_workspace`, `read_agent_file`, `list_agent_files`. `write_agent_file` tool writes files to the agent's home directory with overwrite confirmation flow: if the target exists, the current content is returned and the agent must re-call with `confirm: true`. File tools (`write_agent_file`, `write_workspace`, `read_workspace`, `read_agent_file`, `list_agent_files`) report resolved absolute paths in success/error messages so the agent can verify the actual file location. `PromptContext.home_dir` surfaces the agent's home directory absolute path in the system prompt so the agent knows write_agent_file's base path. **Cross-agent file access:** `read_agent_file`, `write_agent_file`, and `list_agent_files` accept an optional `agent` parameter for orchestrator-only cross-agent file access. `resolve_agent_home(agent_param, ctx)` helper validates: (1) `global_home_dir` is `Some`, (2) self-reference short-circuits to `ctx.home_dir`, (3) `is_orchestrator()` guard using `global_home_dir`, (4) `agent::agent_exists()` for path traversal protection. `write_agent_file` confirmation messages include the agent name for cross-agent writes to prevent misdirected retries. System prompt prohibits `run_shell` for agent home directory files — NEVER/BAD/GOOD formula in both `prompt.rs` and `shell-exec` skill prompt.
- **Labels:** `.github/labels.yml` is the canonical label taxonomy (type, priority, component). All issue-creation paths reference it.
- **Async DB:** `AsyncDatabase` wraps sync `Database` with dedicated OS thread + `sync_channel(512)` mpsc channel (closure-based dispatch). Clone-able, Send+Sync. `with_db` releases the mutex before calling `send()` to avoid deadlocks. Integrated into agent loop, tools, and task engine.

## Architecture

- **One container per customer**
- **Three-layer memory model:**
  - Layer 1: Core memory (always in system prompt, agent-editable via `update_core_memory` tool, 2500 token limit, 5 blocks: user_summary, self_model, current_priorities, key_people, workflows)
  - Layer 2: Structured facts (People, Commitments, Preferences, Events — plaintext). Managed via `store_fact`, `update_fact`, `search_memory` tools.
  - Layer 3: Hybrid search (FTS5 full-text + sqlite-vec cosine similarity via Reciprocal Rank Fusion). Optional OpenAI embeddings (text-embedding-3-small, 512 dims). Graceful degradation: hybrid → FTS5-only → LIKE fallback. Indexed on store_fact/update_fact, backfilled on startup.
- **Agent loop:** Max 10 tool steps, 5-minute total timeout, 30s default per-tool timeout (overridable via `Tool::timeout_secs()`). Step-awareness nudge injected at step 8 (conversation mode only) to encourage wrapping up. On max-steps exceeded: continuation turn (tools disabled, 60s timeout) forces a text summary; if that fails, structured fallback shows last 5 tool names with status. Tool call summaries (name, truncated input/output, success, non_zero_exit) persisted in `messages.metadata` JSON column for cross-turn introspection. `non_zero_exit` is set by heuristic detection of `Exit code:` / `Killed by signal:` prefixes from exec handlers; history builder tags these with `[NON-ZERO]` (distinct from `[FAILED]`). History builder appends `<context type="tool_history">` blocks to assistant messages. **Internal tag stripping:** `strip_internal_tags()` in `mika-common::llm` removes echoed internal XML tags (`<context>`, `<callback_result>`, `<task-health>`, `<rewind_reversals>`, etc.) from LLM response text before display and persistence. Applied at `run_loop()` EndTurn extraction, continuation responses, and the `send_message` tool. Uses lazy-compiled per-tag regexes with early-exit fast path when no `<` present. System prompt also instructs the LLM not to echo internal tags (defense-in-depth). Compaction includes tool names in summarization. Multi-modal tool results: `ToolOutput` carries optional `images: Vec<ImageData>` (base64-encoded), converted to multi-block `tool_result` content arrays for the Claude API. Prior-turn images are stripped before each API call to prevent unbounded memory growth. **Deterministic context injection:** Skills with `[context.*]` sections have their data pre-fetched by the engine before the LLM turn. `resolve_contexts()` dispatches to engine-owned handlers by `context_type`, deduplicates across skills, and returns `ContextBlock`s. `apply_context_replacements()` performs single-pass `{{key}}` template substitution on skill prompts (injection-safe — replaced content is never re-scanned). If a `required = true` context fails, the declaring skill is excluded from the turn; if `required = false`, a sentinel message replaces the placeholder. **Required-tools gate:** When keyword-matched skills declare `[constraints] required_tools`, the engine tracks tool calls across all steps; if the assistant produces a text response on `EndTurn` without calling all required tools, the response is rejected and the agent re-prompted once (counts against max_steps). Prevents fabricated results in skill-driven tasks (see #270). **Match-reason conditioning (#265):** `match_skills()` returns `MatchedSkill` wrappers annotated with `MatchReason` (`Keyword`, `AlwaysOn`, `Dependency`). `collect_required_tools()` only collects from `Keyword`-matched skills — `always_on` skills do not enforce constraints unless the user's message also triggered a keyword. If a skill is both `always_on` and has a keyword hit, the reason is `Keyword` (more specific match wins).
- **Exec handler image protocol (`__mika_v1`):** Scripts return images via JSON envelope `{"__mika_v1": {"text": "...", "images": ["/path/to/img"]}}`. Executor validates files (5MB limit, magic-byte check for JPEG/PNG/GIF/WebP), base64-encodes, max 5 images per result. Used by file-reader skill.
- **Long-running exec handlers:** `long_running: true` + `estimated_duration_secs` in `skill.toml`. Conversation mode only (not silent/team). Creates a callback task, injects `__mika_task_id` and `__mika_agent` env vars (MIKA_* scrubbed), spawns detached process, returns immediately. Background monitor marks task failed on non-zero exit (guarded: skips if task already in terminal state). Signal-terminated processes produce `Killed by signal: N` (not fake exit code `-1`). PID recorded for orphan cleanup via `kill_orphan_processes()`. Team engine detects pending grandchild callbacks and suspends/resumes the run.
- **MCP (Model Context Protocol) client:** Connects to external MCP servers at startup via `McpManager`. Configured in `{agent_home}/mcp.json` (Claude Desktop convention). Supports stdio and Streamable HTTP transports (with custom headers for auth). Tools namespaced as `mcp__{server}__{tool}`. Dispatch chain: builtins → skills → MCP → unknown error. MCP tools excluded from silent/heartbeat mode. Child processes use `env_clear()` + allowlist + server-specific env, blocking MIKA_* overrides. Available in CLI ask/chat and server modes. Team agents do not yet support MCP. CLI: `mika mcp add/remove/list/enable/disable`, `--header KEY=VALUE`.
- **Management tools:** 12 tools for multi-agent/team workflows (`create_agent`, `list_agents`, `create_team`, `delete_team`, `update_team`, `delegate_task`, `list_teams`, `run_team`, `get_team_status`, `get_team_history`, `create_work_item`, `update_work_item_status`). `create_agent`, `list_agents`, `create_team` always registered; others (including work item write tools) added when `agents.len() > 1 || !teams.is_empty()`. Orchestrator guards: only default agent or team-listed orchestrators can delegate/run teams; self-delegation blocked. **Work item guard:** `delegate_task` and long-running skills require `work_item_id` referencing an active manual work item. Delegated agents get `default_tools()` only (no management tools). Per-tool timeouts: `run_team` (300s), `delegate_task` (120s). **Delegate session persistence:** `delegate_task` creates a `delegate-{uuid}` session with parent linkage to the orchestrator's session, persists the task as a "user" message and the response as an "assistant" message (or "system" on error), then ends the session — making delegate interactions visible in the dashboard, `unified_timeline` VIEW, and audit trail. `AgentParams` has `global_home_dir` (e.g. `~/.mika/`) distinct from per-agent `home_dir`. **Team conversation continuity:** injects previous run context (goal, agent results, deliverable, critic feedback) into orchestrator's system prompt; skipped on first run.
- **Work item tracking:** 4 tools for tracking work. **Write tools** (orchestrator-only, registered in `management_tools_if_needed()`): `create_work_item` (create trackable items with optional parent/source/reference_url), `update_work_item_status` (validated transitions — see state machine below). **Read tools** (all agents, registered in `default_tools()`): `list_work_items` (list with status/source filters), `check_work_item` (read work item details with optional GitHub PR/issue status enrichment via `github_token`). Work items reuse the `tasks` table with `trigger_type='manual'` + `action_type='none'`. **Status transition state machine:** `pending` → any status; `in_progress` → blocked/completed/cancelled; `blocked` → in_progress/completed/cancelled. Terminal states (`completed`, `cancelled`) cannot transition — enforced in tool layer, not DB. `check_work_item` parses `reference_url` for GitHub PR/issue URLs (`parse_github_ref`), calls GitHub REST API with `github_token` from `ToolContext` (resolved via `Settings::agent_github_token()`: `MIKA_GITHUB_TOKEN` → `MIKA_INVESTIGATE_GITHUB_TOKEN` fallback), graceful degradation when no token (returns work item data without enrichment). 15s timeout override. System prompt teaches two interaction patterns: direct update (user requests status change) and inspect-first (user asks about status, agent checks then waits for confirmation). Five loop-prevention guards: (1) no top-level creation from task context, (2) depth cap of 3, (3) callback turns block all creation, (4) deferred self_dev source, (5) max 5 agent-created items per session (user_request exempt). **Idempotent creation:** `create_work_item` deduplicates on `reference_url` (DB partial unique index `idx_tasks_manual_active_ref_url` on `(agent_id, reference_url)` for active manual tasks) and on label (case-insensitive tool-level pre-check, no DB index for NULL reference_url). Dedup runs after security guards but before session cap — returning an existing item does not consume quota. On dedup hit, returns the existing item ID with "already exists" message and logs `dedup_reused` audit event (distinct from `created`). UNIQUE constraint violation catch as safety net for race conditions. Active work items injected into heartbeat prompt with label sanitization (200 char truncation, `<>`stripping). Partial index `idx_tasks_manual_active` optimizes heartbeat queries.
- **Introspection tools:** 4 read-only tools for agent self-awareness: `query_timeline` (query unified timeline VIEW across messages/audit_events/tasks), `get_session_messages` (retrieve messages from past sessions), `list_audit_events` (list memory mutation audit events), `search_tool_history` (search past tool calls by tool_name, keyword, time range, success status — 30-day retention, 500-char field truncation, 10KB output cap). All registered in `default_tools()`. Non-orchestrator agents are scoped to their own agent_id/sessions. `search_tool_history` uses LIKE with escaped metacharacters (`%`, `_`) for keyword search in `tool_calls.input`/`output` columns.
- **Skills marketplace:** Git-based and local skill distribution via `mika skills install/uninstall/update`. Sources: git URLs, GitHub shorthand (`user/repo`), local absolute paths, `file://` URIs. `resolve_source()` returns `SourceKind::Git(url)` or `SourceKind::Local(path)`. Optional `--link` flag creates absolute symlinks instead of copies (local sources only) — changes reflected immediately. `MarketplaceEntry` has `linked: bool` and `installed_as_dependency_of: Vec<String>` fields (`#[serde(default)]` for backward compat). `SkillCandidate` carries `dependencies: Vec<String>` from manifest. Scans for `skill.toml` (depth <= 2), tracks in `marketplace.lock` (TOML). Four-tier origin: `[built-in]`, `[marketplace]`, `[marketplace/linked]`, `[custom]`. Update dispatch: linked=no-op, local=re-copy, git=re-clone. Symlink-aware uninstall (`remove_file` for symlinks, `remove_dir_all` for dirs). Broken symlink detection in `scan_skills_dir` with startup warning. Self-referential path rejection. ADR-006 (decisions 11-13 for local source and link mode). Built-in `always_on` overrides stored in `skill_overrides` DB table (schema v7); `apply_overrides()` after `scan_skills_dir()`. **Dependency resolution:** `resolve_dependencies()` BFS with cycle detection (max depth 10), same-source sibling resolution, bundled/already-installed passthrough. Install-time: auto-installs transitive deps before primary skills; `--link` propagates to deps from same source; lock file tracks `installed_as_dependency_of` (diamond deps tracked). Uninstall: `find_orphaned_deps()` detects deps no longer needed; `--remove-deps` flag removes orphans without prompting; cascading cleanup for transitive orphans. Runtime: full transitive BFS in `match_skills()` (disabled mid-chain breaks sub-tree). `safe_always_on_skills()` does NOT resolve dependencies — prevents exec/http handlers in autonomous background contexts. `web-search` is `always_on = true` by default. CLI: `mika skills validate [--name <skill>]` for diagnostics. **Per-provider and per-model variants:** Skills can ship model-tuned prompt variants in a two-level directory hierarchy: `{provider}/` and `{provider}/{model}/` under the skill root. Provider directories are named after `ProviderKind` (e.g., `anthropic/`, `openai/`); model directories within use the model name (slashes replaced with `--` via `sanitize_model_dir_name()`, e.g., `anthropic--claude-sonnet-4` for OpenRouter's `anthropic/claude-sonnet-4`). `SkillEntry` carries `provider_overrides`, `model_prompts`, and `model_overrides` maps (all eagerly loaded at scan time). `resolve_prompt(provider, model)` implements two-level fallback: model-specific → root. Provider-level prompts are intentionally not supported — models from the same provider have different prompt requirements. `effective_timeout(provider, model)` follows three-level fallback: model → provider → root. `inject_skills_and_resolve_tools()` takes both `provider_name` and `model_name`. Sparse `skill.toml` in variant dirs overrides `timeout_secs` and `max_prompt_size` only. CLI `mika skills list` shows `[variants: N]` badge (total providers + models); `mika skills info` shows providers with model variants nested underneath; TUI `/skill` shows model variants with tree-style indentation. **Per-skill LLM override:** Optional `[llm]` section in root `skill.toml` with `provider` and `model` fields (both optional, `#[serde(default)]`). `LlmOverride` struct on `SkillManifest`. When a matched skill declares `[llm]`, `resolve_skill_llm_override()` constructs a per-skill `LlmProvider` via `Settings::make_provider_for()` and uses it for the entire `run_loop()` turn. Resolution: skill `[llm]` > per-provider agent config > global default. Conflict detection: multiple different overrides fall back to default with `warn!`. Same-provider short-circuit skips construction. `AgentParams`, `SilentAgentParams`, `TeamAgentParams` carry `settings: Option<&Settings>` for provider construction. Validation: `validate_skill()` checks provider validity and warns on `[llm]` in variant dirs. `warn_missing_llm_api_keys()` emits startup warnings for missing API keys. CLI: `mika skills list` shows `[llm: provider/model]` badge; `mika skills info` shows LLM Override section. **Required tools enforcement:** Optional `[constraints]` section in root `skill.toml` with `required_tools = ["tool_name"]` (`#[serde(default)]`). `Constraints` struct on `SkillManifest`. `collect_required_tools()` computes the union across keyword-matched skills only — skills matched solely via `always_on` or pulled in as dependencies do NOT contribute constraints (#265). `run_loop()` tracks `tools_called: HashSet<String>` across all steps; on `EndTurn` with non-empty text, if required tools haven't been called, the engine rejects the response once and re-prompts with a correction message listing the missing tools. Only one retry is allowed to prevent infinite loops. Only enforced on `EndTurn` — `MaxTokens` and `ContentFilter` are unrecoverable. `validate_skill()` emits advisory warnings when `required_tools` references names not in `tools.json` (OK for builtins/MCP tools), and warns if an `always_on` skill with no keywords declares `required_tools` (constraints will never be enforced). **Deterministic context injection:** Optional `[context.<key>]` sections in root `skill.toml` with `type` (engine-owned handler identifier) and `required` (bool, default `true`) fields. `ContextRequirement` struct on `SkillManifest`. Each key maps to a `{{key}}` placeholder in the skill prompt. Before the LLM turn, `resolve_contexts()` dispatches to built-in handlers by type, deduplicates across skills (same key + same type = fetch once; same key + different type = conflict, skip both). Known types: `gh_pr_diff` (extracts first GitHub PR URL from user message, fetches diff via GitHub API with optional `github_token` auth, 15s timeout). Smart truncation for large diffs (200K char budget, ~50K tokens): file-level parsing, non-generated files prioritized by churn density, generated/vendored files deprioritized (lock files, `dist/`, `build/`), UTF-8-safe truncation via `floor_char_boundary()`, omitted files summarized. `apply_context_replacements()` performs single-pass regex replacement (injection-safe). When `required = true` (default) and resolution fails, the declaring skill is excluded from the turn; when `required = false`, a sentinel `(Context unavailable: ... resolution failed)` replaces the placeholder. `validate_skill()` checks: unknown context types fail validation; `{{key}}` placeholders without matching `[context.key]` declarations fail; `[context.key]` without corresponding `{{key}}` placeholder warns. New module: `skills/context.rs`.

- `MIKA_SERVER_LOG_FILE` — File path for mika-server log output (always JSON regardless of `MIKA_LOG_FORMAT`)

Gateway mode (`mika-gateway` binary) additionally requires:
- `MIKA_DATABASE_URL` — Postgres connection string
- `MIKA_TELEGRAM_BOT_TOKEN` — Telegram Bot API token
- `MIKA_TELEGRAM_WEBHOOK_SECRET` — 64-char hex secret for webhook validation
- `MIKA_TELEGRAM_WEBHOOK_URL` — Public HTTPS URL for Telegram webhook delivery
- `MIKA_INTERNAL_TOKEN` — Shared 64-char hex bearer token (same as server mode)

Optional (gateway):
- `MIKA_AGENTS_NAMESPACE` — K8s namespace where agent pods run (default: `mika-agents`). Used for FQDN construction in cross-namespace DNS resolution (`http://mika-{id}.{ns}.svc.cluster.local:8080`). Override for environment-scoped namespaces (e.g. `mika-agents-prd`).
